# Лабораторна 5 — GIL і конкурентність

## 1. GIL

У звичайному CPython Global Interpreter Lock (GIL) дозволяє одночасно виконувати Python bytecode лише одному потоку інтерпретатора. Це не означає, що Python «однопоточний»: потоки корисні для I/O-bound роботи, бо блокувальні операції вводу-виводу можуть відпускати GIL. Для CPU-bound чистого Python конкуренція потоків не дає справжнього паралельного виконання bytecode й може додати накладні витрати.

## 2. Чому `findex` використовує процеси

Індексація `findex` переважно CPU-bound: токенізація, підрахунок частот і оновлення словників виконуються у Python. Окремі процеси мають окремі інтерпретатори та окремі GIL, тому вони можуть виконувати Python bytecode паралельно на різних ядрах. Ціна цього підходу — запуск процесів і передавання даних між ними через pickle. Тому у воркери передаються шляхи до файлів, а не вже прочитані тексти.

## 3. Що саме вимірюється

Для кожної конфігурації запускається прогрів і щонайменше три вимірювання. У таблиці зберігаються медіанні wall-clock результати, CPU time, пікова RSS пам'ять батьківського процесу та окремий час послідовного merge. Speedup обчислюється відносно серійного запуску. Саме такий набір метрик передбачений лабораторною.

## 4. Закон Амдала

Merge виконується послідовно після завершення всіх partial build. Тому навіть ідеально паралельна частина не може зробити весь пошук швидшим безмежно. Якщо частка непаралельної роботи дорівнює `p`, теоретична верхня межа прискорення — `1 / p`. Наприклад, якщо merge займає 20% серійного часу, максимальне прискорення наближається до 5×. citeturn682837view1turn872009view0

## 5. Гонки даних

GIL захищає внутрішні структури CPython, але не бізнес-інваріанти програми. Операція на кшталт `counter += 1` є послідовністю кроків read-modify-write, тому спільний mutable state потрібно синхронізувати `threading.Lock` або не ділити між потоками. Для Lab 5 використовується окремий експеримент `benchmarks/gil_experiments.py`; у README треба записати фактичний результат вашого запуску. citeturn682837view1turn872009view0

## 6. Free-threaded Python 3.13

Python 3.13 має free-threaded build, який можна встановити через `uv` як `3.13t`. Для перевірки використовується `sys._is_gil_enabled()`: на free-threaded інтерпретаторі очікується `False`. У такому середовищі CPU-bound потоки можуть виконувати Python bytecode паралельно, але вимоги до thread-safety стають реальними, а сторонні C-розширення мають бути сумісними з free-threading.

### Race condition

Звичайний CPython:

```text
expected: 2000000
unsafe:   1157000
locked:   2000000
```

Free-threaded CPython:

```text
expected: 2000000
unsafe:   1202847
locked:   2000000
```

В обох режимах несинхронізований shared state дає неправильний результат. `threading.Lock` повертає очікуваний результат.

На Windows для цього проєкту `uv` не знайшов готовий wheel для `kiwisolver==1.5.1`, який входить до dev-залежностей через `matplotlib`, тому створення повного dev environment на `3.13t` вимагало б локальної C/C++ збірки.

Це не завадило виконати потрібні Lab 5 експерименти: вони запускалися через `uv run --python 3.13t --no-dev`, а benchmark, Ruff, Pyright і pytest для звичайного CPython пройшли окремо.

### Підсумок

У звичайному CPython GIL обмежує паралельне виконання CPU-bound Python bytecode у потоках, тому для `findex` на цій машині процеси дали найменший wall time.

У free-threaded Python `3.13t` GIL вимкнений, і два CPU-bound потоки в експерименті отримали майже двократне зменшення wall time порівняно з двома послідовними виконаннями.

Водночас відсутність GIL не робить shared mutable state безпечним: race condition залишається, тому потрібна явна синхронізація або поділ стану.
